# 技能路由

大多数任务翻车不是"做不好"，而是"一开始选错了路"。这个 skill 只做三件事：**拆需求 → 匹配 skill → 记住这次选择**。

## 边界

做：
- 任务型请求，没点名 skill，且有可交付物或外部操作（表格/文档/演示/图片/视频/邮件/浏览器/平台发布）
- 用户直接问"该用什么 skill""有没有能处理 X 的技能"

不做：
- 用户点名了 skill → 直接 `skill` 调用，不走路由
- 闲聊、纯知识问答、一条命令或一次读取就能答的事 → 直接做
- 纯代码改动，不涉及 Office / 媒体 / 外部系统交付 → 直接做

## 第 0 步：先查路由表（每次路由的第一动作）

读 `~/.dsh/skill-router/routes.md`，不存在就当作空表。

- **命中**：需求特征落在某条上，且本次硬约束不与该条"不适用"冲突 → 直接加载该 skill 执行。开场只留一句"按你之前定的，这类用 X"，**不再发问**。
- **未命中** → 走第 1–3 步。
- **命中但 skill 已不存在 / 明显不适用** → 改掉那条、一句话告知、重新匹配。

命中看"需求特征"而不是逐字比对：`把数据做成表格` 和 `这份 CSV 转成 Excel 给我` 是同一条。

## 第 1 步：拆解需求（先在心里拆清楚）

按六个字段拆；给用户看时压缩成一两句，讲多了是噪音。

| 字段 | 要判定的 |
|---|---|
| 交付物 | 文档 / 表格 / 演示 / 图片 / 视频 / 音频 / 邮件 / 一次外部操作 / 只是结论 |
| 对象与领域 | 具体格式（.xlsx/.docx/.pptx）、平台（B站/微信/QQ/浏览器页面）、系统（DSH 自身） |
| 动作 | 新建 / 改写已有 / 检索 / 分析 / 自动化 / 发布 |
| 硬约束 | 保持原样式、指定页数或时长、必须登录某账号、必须离线、语言 |
| 规模 | 单步 / 多步流水线 / 需要外部回调或等待 |
| 关键歧义 | 会导致**选错 skill** 的那一两个点；能用默认值就用默认值，最多问 1 条 |

最常见也最值得问的歧义是**交付物形态**："做个报告"可能是 .docx、.pptx，也可能只是一个网页，这会直接改变 skill 选择；"中文还是英文"不值得问。

## 第 2 步：匹配（宁缺毋滥）

候选来源：**会话里的 available_skills 目录是权威**。只在两种情况下去磁盘核对：
- 用户说"我刚装了某个 skill"
- 目录明显缺项（例如刚被提示需要某种能力）

核对方式：`ls ~/.dsh/skills` 看目录名，必要时读对应 `SKILL.md` 头部的 description。

### 三道硬门槛（任一不过，直接淘汰）

1. **交付物能力**：描述能承接这类产物，而不是只沾领域。
2. **前提条件**：它要的账号、登录、本地依赖、图片输入能力，当前会话真的具备。
3. **不越权**：skill 自己写了"When NOT to use"的，不要硬套。

### 强弱判断

- **强**：同时覆盖"动作 + 对象"。例：要写 .xlsx，而某 skill 的描述就是创建/编辑 Excel。
- **中**：覆盖对象，动作靠它的 instructions 支撑。
- **弱**：只覆盖领域（"和文档有关"）。

只推荐强和中。弱匹配不推荐，最多说明差距。

### 两个决策规则

- **通用优先**：同时有总入口和子技能时（office → office-xlsx、univer → univer-sheet），默认先加载总入口让它分流；只有交付物一眼确定是单一类型时才直连子技能。**例外**：如果候选技能的说明直接写着"先加载 A、再加载 B"，它本身就是跳板，按那条链走，别为了"通用优先"再压一层。
- **只要一个**：一次最多加载 1 个重型 skill，需要第二个先说明理由。

### 0 匹配

直接说"现有 skill 都不合适"，给最多 2 个最接近的 + 它们缺什么，并给出"不用 skill 直接做"的路径。**不要为了不空手而归去凑一个弱匹配。**

### 信号 → 能力类别（找候选时的启发，具体名字以当次目录为准）

| 需求里出现 | 优先看 |
|---|---|
| .xlsx / 表格 / 公式 / 透视 / CSV | 表格类 |
| .docx / 报告 / 合同 / 长文排版 | 文档类 |
| .pptx / 汇报 / 路演 / 幻灯片 | 演示类 |
| 图片、视频、配音、短剧、分镜 | 媒体创作类 |
| 发邮件、收件箱、附件、日程 | 邮件类 |
| 浏览器里的页面、点按钮、填表、抓取 | 浏览器自动化类 |
| 某个平台的登录态与发布（B站/微信/QQ） | 平台连接类，或直接用对应 MCP 工具 |
| 改 DSH 自身（插件、preset、工具、skill） | DSH 文档类 |
| 数据处理、脚本、批处理 | 代码/脚本类（多半不需要 skill） |
| 多个角色、大规模并行、成套流水线 | 编排类 |

## 第 3 步：一次性确认（只在首次）

未命中路由表时，用 `ask_user_question` 问**一个**问题，最多四个选项：

1. 推荐 skill（标注"推荐"）
2. 一个备选
3. 不用 skill，直接做
4. 我自己指定

问句里必须有两样东西：**一句为什么选它**、**一句它接下来会做什么**。不要摆分数、不要列全部候选。

例外：
- 用户说过"随便""你定""别再问我"→ 跳过提问，直接选推荐并写表。
- 没有 `ask_user_question` 时，用一句普通问句结尾，给编号选项。

**确认后**：写表 + 立刻 `skill` 加载执行，不要再来一句"那我现在开始了？"。

## 第 4 步：写路由表（"以后不再问"就靠它）

文件：`~/.dsh/skill-router/routes.md`

一条记录 = 业务语言的需求特征 + 该用的 skill + 边界：

```markdown
- **把表格/数据做成 Excel 交付**（触发词：表格、xlsx、CSV、导出、透视）
  → `office-xlsx`
  - 适用：新建成品、读改写、公式与格式化、导出
  - 不适用：只要一张图或网页里的表格；十万行以上该走脚本
  - 确认：2026-11-20
```

规则：
- **一条只记一个需求类型**，用用户会说的话写特征，不要用 skill 的行话。
- "不适用"必须写，它是防误命中的唯一手段。
- 只写用户确认过的。不预填猜测条目，不记一次性任务的细节。
- 追加即可，不要重排已有条目；超过 20 条时合并同类，最常用的放前面。
- skill 被卸载或改名，当天改掉，不留悬空条目。

## 第 5 步：执行与复盘

- 加载后**完整按该 skill 的 instructions 执行**；中途发现它其实不匹配 → 停下来、说明、回退，别硬凑。
- 做完发现路由表的"适用/不适用"写偏了 → 一句话修正那一条，不要另起一条。
- 不写过程日志。表里只记"下次能直接复用"的判断。

## 第 6 步：记一行日志（每次路由都记）

任务级记录，一次请求一行，追加到 `~/.dsh/skill-router/log.jsonl`：

```bash
python3 ~/.dsh/skill-router/log.py add <<'JSON'
{"request":"用户原话的短摘要","decompose":["交付物：…","动作：…"],"decision":"hit","path":[{"name":"skill-router","kind":"inline"},{"name":"office-xlsx","kind":"skill"}],"loads":1,"artifacts":["产出文件"],"note":"一句话复盘"}
JSON
```

- `decision` 只取四个值：`hit`（命中表、免确认）、`first-confirm`（首次确认）、`new`（无表可命中）、`no-match`（0 匹配）。
- `kind` 只取四个值：`skill`（本次真加载）、`jump`（跳板）、`inline`（已在上下文、没重复加载）、`tool`（直接用工具）。
- `loads` 是本次**真实加载**的 skill 数；命中复用写 0——这个数字用来证明路由确实省了事。
- 写完立刻重渲染看板：`python3 ~/.dsh/skill-router/log.py render --out <工作区>/skill-execution-log.html`
- 日志只记判断和路径，不记贴图、不打全文；一条超过两三行说明记多了。

## 输出风格

- **首次**：不超过 6 行 —— 拆解一句话、推荐 + 理由一句话、备选一句话、问句。
- **复用**：一句话说明用了哪个 skill，然后直接开始做。
- 不输出打分明细，不列"我考虑过的八个 skill"，不贴整张表。

## 反模式

- 用"看起来相关"冒充"能解决"——领域相关不等于能力匹配。
- 同类任务每次都重新问一遍，把"一次确认"做成"每次确认"。
- 用户已点名 skill 还硬走路由。
- 同时加载多个重型 skill 以求保险。
- 表条目写太窄（"帮张三做的报销表"）或太宽（"做文档"），后者会误伤。

## 自检（开口前问自己三句）

1. 它能交付这次要的东西吗？产物形态真的匹配吗？
2. 它现在就能用吗？账号、依赖、模型能力齐吗？
3. 用它比直接做更省事吗？如果答案是否，"不用 skill 直接做"就是正确选项。
